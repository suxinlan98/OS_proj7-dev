# 基线审计与重构约束（`docs/baseline/`）

本目录归档在启动 **xv6 双架构微内核重构**（见 [微内核架构设计](../architecture/README.md)）之前，对原始仓库基线代码（xv6-riscv rev5 + 2026 北航扩展版 VFS / HAL / LoongArch64）进行全仓库只读深度审计的完整结论。

本目录承接原单文件 `docs/baseline_debug.md`，并将其按“**现状缺陷**”与“**架构陷阱**”严格解耦为两份独立文档，便于团队一边按清单修 Bug、一边对照红线推进微内核拆分。

---

## 一、目录文件说明

| 文件 | 定位与职责 | 核心内容 |
| :--- | :--- | :--- |
| [`bugs.md`](bugs.md) | **基线缺陷诊断与修复清单**（执行向） | 收录原始基线中真实存在的全部 **57 项代码缺陷**（16 项 P0、34 项 P1、7 项 P2，现已全部完成前置修复并通过双架构验证），按 HAL/VM/驱动、VFS/文件系统/块层、进程/ELF/管道/锁/控制台、构建/用户态/测试框架四大类别展开，附原始基线精确行号与修复提交记录。 |
| [`traps.md`](traps.md) | **双架构与微内核重构工程陷阱手册**（设计向） | 收录 **21 项隐蔽工程陷阱**（`TRAP-01` ~ `TRAP-21`），聚焦双架构硬件差异、用户态驱动 MMIO/DMA 隔离、中断转发闭环、VFS/WAL 拆分耦合、极限压测资源预算及构建测试流水线约束，附重构前架构红线 Checklist。 |

> **分工边界**：
> - 凡属**当前基线代码中已存在的编译、运行、并发、内存安全、文件系统语义或测试脚本错误**，一律记入 `bugs.md`；
> - 凡属**微内核化拆分、双架构硬件机制差异、系统级资源预算或验证契约带来的架构约束**，一律记入 `traps.md`。

## 二、审计基线快照

- **基线提交**：`e5fcf65` / `4b1dda0`（原始未改动基线）
- **目标架构**：RISC-V 64（Sv39 + PLIC + VirtIO-MMIO）与 LoongArch64（4 级页表 + LS7A APIC / EXTIOI + VirtIO-PCI）
- **基线内核体量（~11,471 LOC）**：
  - 文件系统与块缓冲层：~4,193 LOC（`ext2.c` / `fat32.c` / `fs.c` / `vfs.c` / `log.c` / `bio.c` / `block.c`）
  - 设备驱动层：~1,193 LOC（`virtio_disk.c` / `arch/loongarch/virtio_pci.c` / `console.c` / `uart.c`）
  - 文件描述符 / 管道 / 系统调用适配层：~845 LOC（`sysfile.c` / `file.c` / `pipe.c`）
  - 核心内核与双架构 HAL：~5,240 LOC

## 三、协作与维护规范

1. **按清单推进基线修复（`bugs.md`）**：
   - 建议严格按 `bugs.md` 第六节的四阶段路线图推进：**构建与双架构启动止血 → 内核内存安全与并发 P0 → 双架构一致性与测试可信度 P1 → 边界健壮性 P2**。
   - 每完成一项修复并通过双架构编译与对应 QEMU 回归测试后，将该条目的 `- [ ]` 更新为 `- [x]`，并在标题后或条目内注明修复提交的短 hash 与实测验证命令。
2. **微内核改造前对照红线审查（`traps.md`）**：
   - 设计或实现 `vmfault_proc`、用户态 MMIO/DMA 映射、中断转发、`vfsd`/`ext2d`/`fat32d` 协议、`kexec-via-IPC` 与 `rs` 监管槽位前，先核对 `traps.md` 对应章节与文末红线 Checklist。
   - 若在开发过程中验证了新的硬件/并发陷阱或推翻了既有假设，直接补充或校准 `traps.md`，保持文档与代码同步演进。
3. **验证与同步约定**：
   - 任何单点修复均须串行通过 RISC-V 与 LoongArch64 双架构 `-Wall -Werror` 干净构建，不放宽编译告警、不篡改既有测试断言。
   - 若更新本目录结构或文件名，须同步检查根目录 `AGENTS.md` 与 [微内核架构设计](../architecture/README.md) 中的相对链接，并运行 `python3 .github/scripts/check_repo.py` 验证无断链。
